# AGENTS.md

Instructions for AI coding agents working in this repo. Humans: see README.md (Spanish).

## What this is

Agua GDL sends free Telegram reminders before each block of cuts of SIAPA's water rotation in Guadalajara (Oct 2026 – Mar 2027): a notice two days before and a reminder the evening before. It also runs the neighbours' report map and collects "how did the water come back" reports. WhatsApp ran until 15 Oct 2026, when Meta closed the account; its code stays, off without `WA_TOKEN`. It's a civic project: no official affiliation, nonpartisan.

## Layout

- `api/`: Go module `aguagdl/api` (Go 1.27, pgx v5). Entry points `cmd/server` (API, webhook, nightly reminders, daily purge) and `cmd/notify` (sends `cambio_rotacion` to one zone, or with `-tomorrow` tomorrow's reminder as a normal text to the zone's subscribers inside WhatsApp's 24-hour window, reserved in `reminder` so the nightly run won't repeat it, or with `-avisos`, once, the message telling Telegram subscribers about the notice two days before; dry run unless `-send`, and a dry run doesn't migrate the database; run by the maintainer, see README).
  - `internal/rotation`: schedule math and Spanish date formatting. Times are always `America/Mexico_City` (UTC−6, no DST); binaries embed `time/tzdata`.
  - `internal/geo`: zone lookup by point on SIAPA's map (`api/data/colonias_siapa.topo.json`, a copy of `web/colonias_siapa.topo.json`; the test fails if they differ): inside a colonia outline, the zones SIAPA's map gives that colonia (only the side of a split colonia the point is on; none when the map leaves it out), else SIAPA's zone polygons. SIAPA sets colonias' zones by hand, so many it paints lie outside its zone polygons (VALLARTA NORTE, zone 6).
  - `internal/colonias`: name normalization and fuzzy search.
  - `internal/wa`: WhatsApp Cloud API client, webhook types, signature check.
  - `internal/tg`: Telegram Bot API client, update types, webhook secret check. The token is in every request URL, so errors never include the URL. A request that never got a connection (DNS, dial, TLS) fails with `NotSentError`, which counts as refused: the runner waits and retries it, and the run retries it later; anything after the connection stays uncertain.
  - `internal/bot`: inbound message routing for both channels: `Handle` (WhatsApp) and `HandleTelegram` feed the same handlers, which reply with channel-neutral `Reply` values rendered per channel. **All user-facing Spanish copy lives in `internal/bot/messages.go`** (WhatsApp-style `*bold*`; Telegram gets it as HTML). Replies are stored in `pending_reply` (with their recipient) in the same transaction as the command and its deduplication marker, then one statement claims them, commits, and each is sent and deleted: a refused reply (e.g. Telegram's 429, or a connection the webhook's deadline cut) is released, with the replies not yet sent, and the webhook's redelivery sends it without replaying the command; one that may have been delivered (timeout, 5xx) is deleted as if sent, and one claimed when the process died stays claimed until the purge: neither is resent. `Unsubscribe` deletes the replies queued for that person, so an earlier confirmation can't follow the goodbye. Unsent replies hold the chat ID and text, so the daily purge deletes them after a day (the privacy notice says so). Typed answers to the reminders (sí, ya no, poca, baja presión…) get a pointer to the buttons and to BAJA: «Ya no» used to be a stop word, and the report button reads «Poca presión» so a typed «baja» isn't confused with it. Answer buttons that name a zone (`A:zone:…`, `R:zone:…`) end in an 8-character HMAC of chat, kind, zone and date (`SignButtons`, keyed from `TG_WEBHOOK_SECRET` at startup): the bot believes a button's zone only if it's the subscriber's own or the signature checks out, so made-up callback data can't answer for another zone, while a report still counts for the zone it was asked about after a zone change. Whoever subscribes on a cut day in the middle of a block is told the rest of its cuts in the confirmation, since no message comes for them. The confirmation and the greeting name the next message the nightly run will send, so they leave out the reminder it skips for whoever answered «No».
  - `cmd/calendars`: writes `web/calendario/zona-N.ics` (subscribable calendars linked from /mizona) from `rotation.json`; run it from `api/` whenever the rotation changes. `internal/calendar`'s test fails if the published files are stale.
  - `cmd/informe`: run on Mondays from `api/` with `DATABASE_URL` (it only reads). It counts last week's map reports by colonia (`internal/informe`: answers, turbia/olor/sedimento, and the days with «sin agua» reports beside the cut days SIAPA's calendar gave the colonia's main zone) and the bot's answers by zone (the split only from `-min`, as `MIN_REPORTS_SHOWN`), writes `web/semana/<Monday>.html` and `.csv` from `web/informes.html`'s head and footer, relists the weeks between that page's `<!--INFORMES-->` markers and prints the email the maintainer sends to SIAPA, the CEA, the municipios, the Congreso and the CEDHJ. It is off until there are enough reports: on 20 Oct 2026 `web/informes.html` (the shell it needs) and every mention of a Monday count (the landing, /reportes, /exige, the privacy notice, the Telegram description) were removed. Restore them from git history (`cf999bf`) before running it again.
  - `cmd/tgsetup`: one-off; sets the Telegram webhook (with `TG_WEBHOOK_SECRET`), name, descriptions (at most 120 and 512 characters) and command menu; re-run it after changing them. It keeps the updates Telegram holds for the webhook unless `-drop-pending`.
  - `internal/reminders`: the nightly 20:00 sender, caps and heartbeat. It works by blocks of cuts: cut days at most `rotation.BlockGap` (2) days apart, since neighbours report the water goes a day early and takes days to come back (zone 1's Wed–Fri–Sun is one block; so are zone 5's Tue–Wed and zone 7's weekend). Each evening a subscriber gets at most one of: on Telegram, a notice two days before a block (notice key `previo:<first day>`); the reminder the evening before it, skipped for whoever answered «No»; on Telegram, the evening after a block, «¿Ya regresó?» with REPORTAR's answers to whoever answered «No» or «Poca» and hasn't reported since (`regreso:<first day>`), but not on a night their zone gets a notice. Notices and reminders ask «¿Ahorita tienes agua?» with three buttons (`A:zone:date:answer`); answers go to `water_report`, one per subscription and block, only from a subscription that was sent that block's notice or reminder, and «No» gets the pipa contacts (`msgPipa`: SIAPATEL and a link to /pipas). Since 20 Oct 2026 the welcome (headed «El agua es un derecho. Exígelo.»), the help and the confirmation lead with the reports map (/reportes), /exige and PIPA, and the reply to «No» and «Poca» links the map and /exige; the reminders come second. The calendars' alarms follow the same blocks. Unlike WhatsApp's approved template, the Telegram texts quote SIAPA («por máximo un día», «no serán cortes totales») instead of stating it as fact. The notice, like the reminder, skips whoever subscribed after the run hour, so BAJA and subscribing again can't repeat it when a run retries.
  - `internal/notices`: one-off templates to a zone (`cambio_rotacion`), reserved in the `notice` table with the same guarantees as reminders.
  - `internal/webreports`: the reports people make on /reportes (no account): one colonia (`name|municipio|cp`, as listed in `api/data/colonias_mapa.json`), an answer (sin_agua, baja, con_agua) and optional turbia/olor/sedimento. They live in memory for the map (`GET /v1/reportes` builds the last 24 hours, the all-time count and the bot's answers by zone from memory, cached 30 s) and reach Postgres (`web_report`) in batches every 15 minutes and at shutdown, so map traffic doesn't keep Neon awake; the bot's answers are re-read at most every 30 minutes and only while someone is looking. `POST /v1/reportes` accepts only the site's origin (and localhost; any script can claim it, so the limits do the work) and limits each IPv6 /64 to 3 reports per colonia and 20 in all per hour, each /56 to 40 and each /48 to 100, and each IPv4 address, which carriers and home providers share among many customers, to 10 and 100, held in memory only, forgotten after about an hour (Run sweeps them every minute), and never stored; one colonia takes at most 30 an hour from everyone (429 «colonia»), and everyone together 5,000 an hour (503), which bounds memory and the database however many addresses send. Cloudflare Turnstile would stop scripts, but needs keys, the CSP and the privacy notice. The summary also carries the week (`semana`): the last 7 days by zone and day, from the map's reports (in their colonia's main zone; zone 0 is outside the rotation) and the bot's answers (`water_report`, `cut_report`), beside SIAPA's cut days (`Board.Cuts`), each day's split only from `MIN_REPORTS_SHOWN` and only when its bot answers are none or at least that many (the map's counts are public by colonia, so subtracting them could give a few answers away), and how many of the map's «sin agua» came on cut days and on other days (the bot's answers stay out: it asks only on evenings that aren't its zone's cut days); it's re-read with the bot's answers. A changed bot answer replaces the earlier one and counts on the day it was changed. The summary is encoded once per refresh, plain and gzipped.
  - `internal/store`: Postgres, with embedded SQL migrations in `internal/store/migrations` (add new numbered files; never edit applied ones). `Migrate` holds a Postgres advisory lock so two machines starting at once don't race; that needs a direct connection, so `DATABASE_URL` must be Neon's non-pooler URL.
  - `internal/fake`: in-memory test doubles.
- `api/data/`: embedded data. `rotation.json` is the schedule (update `checked`/`checked_by` when you change it); `colonias.json` is generated by `pipelines/siapa_colonias.py`; `colonias_siapa.topo.json` is the copy of SIAPA's map the API looks zones up in (`pipelines/siapa_mapa.py` writes it with the web copy); `otras_colonias.json` (names from INE, by `pipelines/colonias_poligonos.py`) takes its zones from SIAPA's map through `pipelines/mapa_colonias.py`; `zonas.geojson` is the old My Maps KML's zones (`pipelines/siapa_zonas.py`), which SIAPA's page no longer shows: the API doesn't read it, only `colonias_poligonos.py` (INE outlines missing from SIAPA's map) and `zonas_preview.py` (the landing's `web/zonas.svg`).

## Rules

- Never send real WhatsApp or Telegram messages from tests or local runs. `REMINDERS_ENABLED` and `TG_REMINDERS_ENABLED` stay false unless the maintainer turns them on in production.
- Channels: `subscriber.channel` is `wa` or `tg` (one subscription per channel and user ID); `reminder` and `notice` rows carry the channel too. Meta's caps and `NightCap` count WhatsApp only. The runner sends each enabled channel independently. A Telegram 403 (bot blocked) deletes the subscription and marks the attempt `blocked`; a 429 is waited out (nothing was sent).
- Don't relax the safety rails: idempotent sends per (subscriber, cut date), daily and monthly caps, the heartbeat, never resending an attempt WhatsApp may have accepted (only `rejected` attempts are retried), and the webhook signature check. A duplicate or missed reminder is the worst bug here.
- Caps: `DAILY_CAP` counts distinct recipients in a moving 24 hours, like Meta's messaging limit (250 for a new portfolio), across reminders and notices; when it's full the runner waits for the window instead of skipping anyone, and gives up only at `CATCH_UP_UNTIL_HOUR`. The bot refuses a subscription or zone change that would push any night over `DAILY_CAP` (`msgFull`). Raise `DAILY_CAP` only after Meta raises the portfolio's limit. `MONTHLY_CAP` counts messages (cost). Every WhatsApp reservation (nightly run, `notify`, `-tomorrow`) re-checks both caps under one Postgres advisory lock (`store.Budget`), so concurrent senders can't overshoot them; the admission check holds its own lock (`ZoneCounts`) through the subscription. Reports: only a subscription that already existed when a cut began can report that cut, so BAJA and subscribing again can't add reports. After `rotation.Expired` the bot refuses new subscriptions and zone changes, and its welcome says the rotation is over (BAJA still works).
- Privacy: store only the phone number, zone and consent time. BAJA must delete the subscriber; reports stay anonymous. Reports from /reportes never carry an IP, a location or a subscriber. A phone number belongs to at most one subscription, the one Meta most recently tied to it (partial unique index, migration 005): `Subscribe` and `ChangeUser` drop any other row holding it, and BAJA deletes every row with the sender's ID or number. Thirty days after `end` in `rotation.json` the server deletes every subscriber (`rotation.Expired`), as the privacy notice promises: move `end` if SIAPA extends the rotation. Never log phone numbers or WhatsApp message IDs: a wamid embeds the phone number, so the database stores only its SHA-256. No secrets in the repo; config comes from env vars (see `.env.example`).
- Public API protections: `/v1/*` allows 120 requests per minute per client IP (`Fly-Client-IP`, set by Fly's proxy; api.aguagdl.com is DNS-only, not behind Cloudflare's proxy) and, past 10,000 addresses in a minute, 1,200 shared among the new ones; `/v1/results` reuses one query for 5 minutes so web traffic can't keep Neon awake and burn its free compute hours; and `/v1/zone` is `no-store` because it carries coordinates. `/v1/reportes` serves from memory, and its POST has its own per-address limits and an origin check (see `internal/webreports`). Keep them when you add endpoints.
- WhatsApp templates are approved by Meta. If you change the parameters or buttons the code sends, the template in WhatsApp Manager must change too.
- Keep code comments sparse and match the surrounding style. Commit messages in English. User-facing copy in plain Mexican Spanish.
- Don't force-push. The maintainer may be editing in parallel: check `git status` before you edit or commit.
