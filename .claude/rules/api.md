# api/: Go module `aguagdl/api` (Go 1.27, pgx v5)

- `cmd/server`: the API, the webhooks, the nightly reminders and the daily purge.
- `cmd/notify` (run by the maintainer, see README): sends `cambio_rotacion` to one zone; `-tomorrow` sends tomorrow's reminder as a plain WhatsApp text inside the 24-hour window, reserved in `reminder` so the nightly run won't repeat it; `-avisos` sends the one-off message about the notice two days before (never sent). Dry run unless `-send`; a dry run doesn't migrate the database.
- `cmd/calendars`: writes `web/calendario/zona-N.ics` (subscribable calendars linked from /avisos) from `rotation.json`. Run it from `api/` whenever the rotation changes; `internal/calendar`'s test fails if the published files are stale. An all-day event starts at 00:00 of the cut day, so its alarms count back from midnight: 20:00 two days before is `-P1DT4H`. Check an alarm's instant against the bot's notice time, not against the words «dos días».
- `cmd/tgsetup`: one-off; sets the Telegram webhook (with `TG_WEBHOOK_SECRET`), name, descriptions (at most 120 and 512 characters) and command menu. Re-run it after changing them. It keeps the updates Telegram holds for the webhook unless `-drop-pending`.
- `cmd/informe` (with `internal/informe`): reads production Postgres and writes the Monday count of last week's map reports and bot answers (`web/semana/`), updates `web/informes.html` and prints the email for SIAPA, the CEA, the municipios, the Congreso and the CEDHJ. Generate, review and publish a week only when it has enough reports; the index says when none has been published. The two bot questions have separate denominators and privacy thresholds, and the pages never claim representativeness, causation or laboratory water quality.
- `internal/rotation`: schedule math and Spanish date formatting. Times are always `America/Mexico_City` (UTC−6, no DST); binaries embed `time/tzdata`. A block of cuts is cut days at most `BlockGap` (2) days apart, since neighbours report the water goes a day early and takes days to come back (since 4 Nov: zone 1's Thu–Mon is one block; so are zone 5's Mon–Thu and zone 7's weekend). `Over` is true from the day after `end`, `Expired` from thirty days after it.
- `internal/geo`: zone lookup by point on SIAPA's map (`api/data/colonias_siapa.topo.json`, a copy of `web/colonias_siapa.topo.json`; the test fails if they differ). Inside a colonia outline, the zones SIAPA's map gives that colonia (only the side of a split colonia the point is on; none when the map leaves it out), else SIAPA's zone polygons. SIAPA sets colonias' zones by hand, so many lie outside its zone polygons (VALLARTA NORTE, zone 6).
- `internal/colonias`: name normalization and fuzzy search. `internal/wa`: WhatsApp Cloud API client, webhook types, signature check.
- `internal/tg`: Telegram Bot API client, update types, webhook secret check. The token is in every request URL, so errors never include the URL. A request that never got a connection (DNS, dial, TLS) fails with `NotSentError`, which counts as refused: the runner waits and retries it, and the run retries it later; anything after the connection stays uncertain.
- `internal/bot`: inbound routing for both channels. `Handle` (WhatsApp) and `HandleTelegram` feed the same handlers, which reply with channel-neutral `Reply` values rendered per channel.
  - **All user-facing Spanish copy lives in `internal/bot/messages.go`** (WhatsApp-style `*bold*`; Telegram gets HTML). What the user typed is echoed without `*` and `_`, since Telegram refuses a message whose tags don't nest.
  - Replies go to `pending_reply` (with their recipient) in the same transaction as the command and its deduplication marker; one statement then claims them, commits, and each is sent and deleted. A refused reply (Telegram's 429, or a connection cut by the webhook's deadline) is released with those not yet sent, and the webhook's redelivery sends it without replaying the command; one that may have been delivered (timeout, 5xx), or was claimed when the process died, is never resent. `Unsubscribe` deletes the person's queued replies, so a confirmation can't follow the goodbye. The daily purge deletes unsent replies, which hold the chat ID and text, after a day (the privacy notice says so).
  - Typed answers (sí, no, ya no, poca, baja presión…) get a pointer to the buttons, to the location (the bot is stateless, so a «no» may answer «¿Es la tuya?») and to BAJA. «Ya no» is not a stop word, and the report button reads «Poca presión» so a typed «baja» isn't confused with it.
  - Buttons that name a zone (`A:zone:…`, `R:zone:…`) end in an 8-character HMAC of chat, kind, zone and date (`SignButtons`, keyed from `TG_WEBHOOK_SECRET`): the bot believes the zone only if it's the subscriber's own or the signature checks out, so made-up callback data can't answer for another zone, while a signed report still counts for the zone it was asked about after a zone change. An older unsigned report button can't report a cut from before the latest subscription or zone change. Callback data fits Telegram's 64 bytes; a test checks every colonia in `colonias.json`, the only list offered as buttons.
  - The confirmation lists the rest of a block under way (no message comes for those cuts), and the confirmation and the greeting name the next message the nightly run will send, leaving out the reminder it skips for whoever answered «No». Once the rotation is over, a subscriber's greeting offers only BAJA.
  - It subscribes only to zones the schedule has days for: a spot or a colonia without one gets `msgOutside` or `msgColoniaOutside`.
- `internal/reminders`: the nightly 20:00 sender, caps and heartbeat. Each evening the three senders run independently: on Telegram, a notice two days before a block (notice key `previo:<first day>`); the reminder the evening before it, skipped for whoever answered «No»; on Telegram, the evening after a block, «¿Ya regresó?» with REPORTAR's answers to whoever answered «No» or «Poca» and hasn't reported since (`regreso:<first day>`), but not on a night their zone gets a notice. A subscriber can get both the regreso question and the next block's reminder the same evening; within one sender a person gets at most one message per block/key.
  - Notices and reminders ask «¿Ahorita tienes agua?» with three buttons (`A:zone:date:answer`); answers go to `water_report`, one per subscription and block, only from a subscription that was sent that block's notice or reminder, and «No» gets the pipa contacts (`msgPipa`: SIAPATEL and /pipas).
  - The welcome, the help and the confirmation lead with the reports map, /exige and PIPA; the bot's profile description is «El agua es un derecho. Exígelo.»; the reply to «No» and «Poca» links the map and /exige; the reminders come second. Unlike WhatsApp's approved template, the Telegram texts quote SIAPA («por máximo un día», «no serán cortes totales») instead of stating it as fact.
  - The notice, like the reminder, skips whoever subscribed after the run hour, so BAJA and subscribing again can't repeat it when a run retries. The calendars' alarms follow the same blocks.
- `internal/notices`: one-off templates to a zone (`cambio_rotacion`), reserved in the `notice` table with the same guarantees as reminders.
- `internal/webreports`: the reports people make on /reportes (no account): a colonia (`name|municipio|cp`, from `api/data/colonias_mapa.json`), an answer (sin_agua, baja, con_agua) and optional turbia/olor/sedimento.
  - Each report gets a random receipt and is fsynced to `REPORT_WAL` (default `/data/web-reports.wal`) before acknowledgement. The JSON-lines WAL contains the report and receipt, never an IP; startup replays it, Postgres de-duplicates receipts transactionally and successful flushes compact it atomically. Production requires a persistent `/data` volume and exactly one active API/reminder instance. Reports are also held in memory and written to Postgres (`web_report`) every 15 minutes and at shutdown, so map traffic doesn't wake Neon. `GET /v1/reportes` builds from memory the current 24 hours (`colonias`), the previous 24–72 hours for colonias with nothing current (`anteriores`, each with its latest answer), the all-time count, the bot's answers by zone and the week, cached 30 s and encoded once (plain and gzipped); the bot's answers are re-read at most every 30 minutes, only while someone is looking. Reports older than 72 hours leave the live memory but stay in Postgres.
  - `POST /v1/reportes` accepts only the site's origin (and localhost; any script can claim it, so the limits do the work). The hourly limits per IPv6 /64, /56 and /48 and per IPv4 address (looser, since carriers and home providers share one among many customers) are the constants at the top of `webreports.go`. A colonia takes reports from at most 30 networks an hour (an IPv4 address or an IPv6 /48 counts once and puts at most 10 into it), so no single network can fill it and lock its neighbours out; everyone together gets 5,000 an hour. Addresses and networks live in memory only, so a restart clears them; they're forgotten after about an hour and never stored (the privacy notice says so). Cloudflare Turnstile would stop scripts, but needs keys, the CSP and the privacy notice.
  - The week (`semana`) puts the last 7 days of map reports (in their colonia's main zone) and bot answers (`water_report`, `cut_report`) beside SIAPA's cut days (`Board.Cuts`), and exposes the map's daily counts by colonia in `reportes` for the timeline. Map-only daily splits show from `MIN_REPORTS_SHOWN`; days containing bot answers and the bot's 24-hour results publish totals only, never exact bot splits, so snapshots and restarts can't reveal a small group by differencing.
- `internal/store`: Postgres, with embedded SQL migrations in `internal/store/migrations` (add new numbered files; never edit applied ones). `Migrate` holds a Postgres advisory lock so two machines starting at once don't race; that needs a direct connection, so `DATABASE_URL` must be Neon's non-pooler URL. `subscriber_zone` is the authoritative set of memberships; `subscriber.zone` is only the latest/primary compatibility field. A person may follow several zones, gets at most one reminder or notice per block/key, and can remove one with `BAJA ZONA N` or all with `BAJA`. Nightly admission and daily caps count distinct recipients across coincident zones.
- `internal/fake`: in-memory test doubles. Keep them behaving like the real store and clients: `SaveReport` keeps one report per subscription and cut, and `Telegram.Send` refuses, as Telegram does, HTML whose tags don't nest and callback data over 64 bytes.

## Rules for api/

- Channels: `subscriber.channel` is `wa` or `tg` (one subscription per channel and user ID); `reminder` and `notice` rows carry the channel too. Meta's caps and `NightCap` count WhatsApp only. The runner sends each enabled channel independently. A Telegram 403 (bot blocked) deletes the subscription and marks the attempt `blocked`; a 429 is waited out (nothing was sent).
- Safety rails, in full: idempotent sends per (subscriber, cut date), daily and monthly caps, the heartbeat, never resending an attempt WhatsApp may have accepted (only `rejected` attempts are retried), and the webhook signature check.
- Caps: `DAILY_CAP` counts distinct recipients in a moving 24 hours, like Meta's messaging limit (250 for a new portfolio), across reminders and notices; when it's full the runner waits for the window instead of skipping anyone, and gives up only at `CATCH_UP_UNTIL_HOUR`. The bot refuses a subscription or zone change that would push any block-start night over `DAILY_CAP` (`msgFull`). Raise `DAILY_CAP` only after Meta raises the portfolio's limit. `MONTHLY_CAP` counts messages (cost). Every WhatsApp reservation (nightly run, `notify`, `-tomorrow`) re-checks both caps under one Postgres advisory lock (`store.Budget`), so concurrent senders can't overshoot them; the admission check holds its own lock (`ZoneCounts`) through the subscription. Reports: only a subscription that already existed when a cut began can report that cut, so BAJA and subscribing again can't add reports; an unsigned button also can't report a cut from before the latest zone change. From the day after the rotation's `end` (`rotation.Over`) the bot refuses new subscriptions and zone changes, and its welcome says the rotation is over (BAJA still works).
- Privacy, in full: a phone number belongs to at most one subscription, the one Meta most recently tied to it (partial unique index, migration 005): `Subscribe` and `ChangeUser` drop any other row holding it, and BAJA deletes every row with the sender's ID or number. Thirty days after `end` in `rotation.json` the server deletes every subscriber (`rotation.Expired`), as the privacy notice promises: move `end` if SIAPA extends the rotation. A wamid embeds the phone number, so the database stores only its SHA-256. Config comes from env vars (see `.env.example`).
- Public API protections: `/v1/*` allows 120 requests per minute per client IP (`Fly-Client-IP`, set by Fly's proxy; api.aguagdl.com is DNS-only, not behind Cloudflare's proxy) and, past 10,000 addresses in a minute, 1,200 shared among the new ones. Neon suspends after 5 idle minutes, so anything a stranger can trigger every few minutes would keep it awake and burn its free compute hours: public endpoints serve from memory, and what they read from Postgres is refreshed at most every 15–30 minutes. POST `/v1/zone` and `/v1/colonias` are `no-store`; reject NaN and infinite coordinates. Keep all of this when you add endpoints.
- WhatsApp templates are approved by Meta. If you change the parameters or buttons the code sends, the template in WhatsApp Manager must change too.
- Tests give the code a fixed `Now` inside the rotation, never the wall clock: with the real `rotation.json`, a test that reads the clock breaks when the rotation ends, and the weekly CI run goes red with no change.
